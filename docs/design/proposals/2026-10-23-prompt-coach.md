# 提案: prompt-coach（送ったプロンプトの弱点を 1 行で指南する）

作成: mods-lab / 2026-10-23 / 状態: **提案のみ（GO 待ち。コード・PR なし＝本 PR は docs のみ）**
優先度: **仮置き 3 位**（需要は本人の体感ベース。実データの裏取りは未実施）

## 1. 困りごと
- **誰が・いつ**: だいすけが、対象や完了条件を省いた短い指示を送ったとき。モデルは推測で進めるので、
  - 意図と違う実装が返り、**手戻りの 1 往復**が発生する
  - 的外れな探索で**ファイルを大量に読み、コンテキストを浪費**する
  - 1 通に複数の依頼を詰め、**どれかが落ちる**
- **具体例（想定シナリオ。実際の入力履歴の集計はしていない）**

| 送った文 | 起きがちなこと（仮説） | 足すと良い一言 |
|---|---|---|
| 「これ直して」（セッション 1 通目） | 「これ」が何か分からず探索から始まる | 対象ファイル / エラー文 |
| 「リファクタして」 | 範囲と守る制約が無く、広く書き換える | 範囲・触らないもの |
| 「認証を追加して、テストも、READMEも、あとCI」 | 4 件が並び、後ろが落ちる | 1 通 1 ゴールに分ける |
| 「いい感じにして」 | 完了条件が無く、止め時が不明 | 完了の判定（テスト通過など） |

- 注意: 上表の「起きがちなこと」は**仮説**。曖昧な指示で本当に手戻りが増えるかは、本人の履歴で未検証（§3 で観察と仮説を分ける）。

## 2. 使う場面と表示イメージ
- **いつ**: 人が Enter で送った直後（`prompt.submit`）。ルールに当たったときだけ。
- **どこに**: プロンプト下の status 行（`$.ui.status`）。ターン中だけ表示、次のターンで消える。入力は**止めない・書き換えない**。
- **長さ**: 1 行（全角 60 字目安）。理由 + 次回の一言。

```
> リファクタして
  ...（モデルが作業中）...
 💡 範囲が無いまま「リファクタ」だけ。次回は「<ファイル>の<関数>だけ、<制約>を守って」と添えると手戻りが減りやすい
```
```
> 認証追加して、テストも、READMEも、あとCI
 💡 4 件の依頼が 1 通に並んでいます。1 通 1 ゴールだと取りこぼしが減りやすい
```
- 当たらなければ**何も出ない**。パネル・スコア・ゲージは作らない。
- 目視未確認（UI は実装後に目視確認が必要）。

## 3. 診断の根拠（観察と仮説を分ける）
| 層 | 内容 | 確かさ |
|---|---|---|
| 観察（確実） | 送信文の長さ、パス/拡張子/識別子の有無、箇条・読点で数えた依頼数、指示語（これ/それ）の有無、セッション内の通番、直前ターンのツール使用 | 文字列と型から機械的に得られる |
| 仮説（未検証） | 「それが手戻り・浪費の原因」「足すと改善する」 | **共起を原因と書かない**。表示文も「減りやすい」止まりで断定しない |
| 検証方法 | 実装後、「指摘した送信 → 次の数ターンの読込量・再依頼の有無」を自分の履歴で突き合わせる（相関止まり） | スパイクで実施 |

- **ヒューリスティクス（v1・推奨）**: 上記の観察だけで判定。決定的で再現でき、コストゼロ、プロンプト本文を外に出さない。**弱点**: 「曖昧さ」の意味は理解できない。見逃しと誤検知がある（短い「はい」「続けて」は黙る）。
- **モデル呼び出し（v2・保留）**: 意味を見て的確に指摘できるが、毎ターン費用とレイテンシが乗り、本文がモデルに渡る。§4 参照。

## 4. 必要権限（過小申告しない）
| 区分 | v1（ヒューリスティクス） | v2（モデル判定） |
|---|---|---|
| 読取 | `prompt.submit` の `text`・`origin`、`$.session.messages()`（通番・直前ツール） | 同左 |
| 実行 | なし | なし |
| 書込 | なし（頻度制御の状態のみ。保存先 API の名前空間は**型で要確認**） | 同左 |
| 通信・モデル | **なし** | `$.model.complete` / `$.model.classify`（型に実在）。**費用・本文送信あり** |
- **v1 は読取のみで可能**。**v2 は相談キュー行き**（`open-questions.md` に起票し、だいすけが判断）。なお repo の `CLAUDE.md` はモデル呼び出しを相談対象に列挙していないが、費用と本文の流出を伴うので本件では相談扱いにする。

## 5. しつこさ対策
- **出す条件**: 人が Enter で送ったとき（`origin.kind` で通知・meta を除外）で、ルール 1 つ以上に当たり、かつ下記の黙る条件に当たらない。
- **頻度の上限**:
  - 同じルールは**1 セッション 2 回まで**
  - 全体で**直近 10 通につき 1 回まで**
  - 1 通に出すのは**最大 1 行・ルール 1 つ**（優先順位あり）
- **黙る条件**:
  - スラッシュコマンド、`isMeta`、人以外の起源
  - 短い承認・継続（「はい」「OK」「続けて」「進めて」）
  - 同セッション内で既に対象・文脈が明示済みの追撃
  - ログ・差分などの**貼り付け主体**の送信
  - `/coach off` で全停止（既定は on。`userConfig` で各ルールの on/off）
- **自己修正**: 当てはまる送信が続いても同じ指摘を繰り返さない（上限で自然に減衰）。

## 7. 過去 mod が不評だった理由への回答
| 不評の理由（だいすけ指摘） | 本案の回答 | 残る懸念 |
|---|---|---|
| 役に立たない | 指摘は「次回足す一言」まで具体化。当たったときだけ出す。v1 は誤検知を減らすため**ルール 4〜5 個に絞る** | 効果は仮説。スパイクで自分の履歴と突き合わせ、効かなければ見送る |
| 見た目が悪い | 新しい画面を作らず、既存の status 行に 1 行のみ。装飾・スコアなし | 実際の見え方は**目視未確認**。目視で崩れたら toast に切替 |
| 使う場面がない | 毎日送る「プロンプト」が対象で、常に場面がある。ただし当たる頻度は上限で絞る | 当たらなさすぎると存在感ゼロ。ルール粒度は実測で調整 |
- repo 内に不評の具体理由の記述は無い（`read-trail.md` に「不評」の語のみ）。上記は依頼文の 3 点に基づく。

## 8. 代替案と推奨
| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **A（推奨）: v1 ヒューリスティクス、送信直後に 1 行** | §2〜6 のとおり | 読取のみ・費用ゼロ・即時・本文が外に出ない | 意味は読めず、見逃しあり |
| B: モデル判定（`$.model.classify`/`complete`） | 意味を見て的確に指摘 | 指摘の質が高い | 毎ターン費用・遅延・本文がモデルへ。**相談キュー行き** |
| C: オンデマンドの `/coach`（現セッションの送信を一括講評、自動表示なし） | 呼んだときだけ。しつこさゼロ | 邪魔にならない | 呼ばないと使われない（過去の「使う場面がない」型）。送信直前の指南にならない |

**推奨: A**。理由: 権限が読取のみでリスクが最小、しつこさを数値で制御でき、効果の有無を安く検証できる。A が「効く」と分かったら、判定の質を上げる B を相談キューに上げる。

## 9. 既存 mod・組み込み機能との差
- context-doctor / model-review / repeat-call-notice は**モデルの出力・文脈**を見る。本案は**利用者の入力**を見る（重複なし）。
- 組み込みにプロンプト品質の指南機能があるかは**未確認**。
